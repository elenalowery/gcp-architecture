RAG Pattern — Retrieval-Augmented Generation

Google Cloud Platform

A customer wants to ground LLM responses in a private or domain-specific knowledge base rather than relying solely on model training data. RAG retrieves semantically relevant document chunks at query time, injects them into the LLM prompt as context, and returns a grounded response.

Common Workloads
Enterprise Search & Q&A Customer Support (grounded on docs) Legal / Compliance Copilots Internal Knowledge Assistants Product Documentation Bots Code Repository Search

RAG Core Components

  • Document Ingestion Pipeline — load, chunk, embed, store
  • Embedding Model — converts text to dense vector representations
  • Vector Database — stores and indexes embeddings for ANN retrieval
  • Retriever — fetches top-K chunks by cosine / dot-product similarity
  • LLM (Generator) — synthesises the answer from retrieved context

Knowledge Base Strategies

  • Preloaded (static) — ingested before deployment; ideal for stable document corpora
  • User-loaded (interactive) — users upload documents at runtime; per-session or persistent namespaces
  • Hybrid — static base corpus + user-uploaded supplements in tenant-scoped namespaces
  • Continuous ingestion — event-driven pipeline updates index as source docs change

The knowledge base is built offline — before the solution is deployed — by an ingestion pipeline that processes source documents, generates embeddings, and populates the vector index. At query time, the Client Application retrieves relevant chunks and sends them with the prompt to the LLM.

Fig 1 — Preloaded Knowledge Base (Offline Ingestion → Online Retrieval)

Pros

  • Vector index is fully warm at launch
  • No ingestion latency at query time
  • Simpler query-path architecture

Cons

  • Stale if source documents change
  • Requires re-ingestion workflow
  • Not suitable for user-specific docs

When to Use

  • Stable corpora (manuals, policies)
  • Shared knowledge across all users
  • Compliance-reviewed content only

The Client Application lets users upload documents at runtime. An asynchronous ingestion pipeline processes them in the background. Documents are scoped to a user or session namespace in the vector database so retrievals remain tenant-isolated.

Fig 2 — Interactive (User-Loaded) Knowledge Base

Pros

  • Users enrich context in real time
  • Tenant-isolated namespaces
  • No rebuild of full corpus

Cons

  • Async lag before doc is retrievable
  • Namespace management overhead
  • Risk of PII in user-uploaded content

When to Use

  • Per-user or per-project workspaces
  • Dynamic document sets
  • Self-service knowledge platforms

Architectural Decisions

Google Cloud Platform

1 · Vector Database — GCP Options

Choose based on scale, existing stack, latency SLA, and operational overhead tolerance.

Vector Search — raw vector index infrastructure (ANN); you manage chunking, embedding, and retrieval logic; scales to billions of vectors; lowest latency Search — fully managed, turn-key search pipeline; Google handles chunking, embedding, indexing, and ranking on your private data; least ops overhead AlloyDB for PostgreSQL — pgvector extension; relational + vector in one DB; good for hybrid SQL+semantic queries Cloud Spanner — pgvector support; globally distributed; for globally consistent vector workloads BigQuery — VECTOR_SEARCH function; analytics-scale retrieval; best when docs already in BQ Cloud SQL (PostgreSQL) — pgvector; lowest cost entry point; limited to single-node scale Self-managed on GKE — Weaviate, Qdrant, Milvus, Chroma; full control, full ops burden

2 · Embedding Model Selection

The embedding model must be fixed for the lifecycle of the index — changing it requires full re-ingestion.

text-embedding-004 — Google's latest embedding model; 768-dim; strong multilingual performance; recommended default text-multilingual-embedding-002 — 768-dim; 100+ languages; use for multilingual corpora textembedding-gecko — 768-dim; older generation; lower cost per token Custom fine-tuned embedding model — domain-specific vocabulary (legal, medical, code) Third-party (OpenAI, Cohere via API) — usable but adds external dependency and egress cost

3 · User-Loaded vs. Preloaded Knowledge Base

Determines ingestion architecture complexity and namespace strategy.

Preloaded — single shared namespace; simpler ops; re-ingestion on content change User-loaded (persistent) — per-user namespace; documents survive sessions; storage cost scales with users User-loaded (session-scoped) — ephemeral namespace; auto-deleted after TTL; lower storage cost Hybrid — shared base corpus + user-owned supplement namespaces; search merges both

4 · Asynchronous vs. Synchronous Document Ingestion

Synchronous ingestion blocks the upload response until the doc is indexed; async decouples upload from retrieval availability.

Async (recommended) — GCS upload → Pub/Sub → Cloud Run worker → Vector DB; non-blocking; scalable Async with Dataflow — large-scale batch or streaming ingestion; handles millions of docs Synchronous — inline embed + upsert in the upload request; simple but adds latency and couples concerns Cloud Workflows — orchestrate multi-step ingestion with retries, checkpointing, and visibility

5 · Updating the Vector Index

Stale embeddings degrade retrieval quality. Choose an update strategy that matches how frequently source content changes.

Event-driven upsert — GCS / Firestore change events via Pub/Sub → incremental upsert of changed doc chunks only Scheduled full re-index — Cloud Scheduler triggers Dataflow job; safe for stable corpora; complete consistency Delta ingestion — only new or modified documents since last run; use object versioning or change data capture Soft delete + re-embed — mark old vectors inactive; embed new version; swap at query time via metadata filter Manual re-index — operator-triggered; acceptable only for infrequently updated content Dual-write during migration — write to both old and new index during embedding model upgrades

6 · Observability

RAG quality is invisible without instrumentation at both the retrieval and generation layer.

Gen AI Evaluation Service — automated recall@K, faithfulness, and groundedness scoring Cloud Logging — log query, retrieved chunk IDs, and LLM response for offline audit Cloud Monitoring — p50/p95 retrieval latency, embedding throughput, ingestion lag dashboards Cloud Trace / OpenTelemetry — distributed traces: query → retriever → vector DB → LLM Retrieval quality metrics — precision@K, MRR, NDCG; measure with labelled test queries Chunk-level feedback loop — user thumbs-up/down signals → label store → periodic embedding fine-tune

GCP Vector Database Options — At a Glance

Google Cloud Platform

Vector Search

  • Raw ANN index infrastructure — you own the pipeline
  • You manage chunking, embedding calls, and upserts
  • Scales to billions of vectors; <10 ms p99 latency
  • Supports batch + streaming upserts
  • Maximum flexibility and control

✓ Best for: large-scale workloads needing full pipeline control

Search

  • Fully managed, turn-key search engine pipeline
  • Google manages chunking, embedding, indexing & ranking
  • Operates on private enterprise data (not the open web)
  • Hybrid search (semantic + keyword) built in
  • Grounding API for Gemini; lowest ops overhead

✓ Best for: fastest time-to-value RAG on private data

AlloyDB for PostgreSQL

  • pgvector extension (HNSW / IVFFlat)
  • Combines relational + vector queries
  • Supports hybrid SQL + cosine search
  • 99.99% SLA, columnar engine
  • Good for existing Postgres workloads

✓ Best for: hybrid SQL + semantic retrieval

BigQuery

  • VECTOR_SEARCH() SQL function
  • Embeddings stored as ARRAY columns
  • Scales to analytics-grade data volumes
  • Join with structured data in same query
  • Higher latency vs. dedicated vector DBs

✓ Best for: analytics + RAG on same dataset

Cloud Spanner + pgvector

  • Globally distributed, strongly consistent
  • pgvector interface for vector operations
  • Suits multi-region deployments with strict consistency
  • Higher cost; use only when global replication is required

✓ Best for: globally consistent vector workloads

Self-Managed on GKE (Weaviate / Qdrant / Milvus)

  • Full control over index type, distance metric, sharding
  • Supports advanced features: sparse+dense hybrid, multi-vector
  • Operator team owns upgrades, backups, HA
  • GKE Autopilot reduces node management overhead

⚠ Best for: specialised requirements, not default choice

Selection Summary

Start with Search for fastest delivery — Google manages the full pipeline on your private data. Move to Vector Search when you need raw index control, sub-10 ms latency at billion-vector scale, or a custom retrieval pipeline. Use AlloyDB when you need relational joins alongside semantic search.

Fastest time-to-value → Search (fully managed pipeline) Large scale, custom pipeline → Vector Search (raw ANN index) Relational + vector → AlloyDB pgvector Analytics + RAG → BigQuery VECTOR_SEARCH Global consistency → Cloud Spanner pgvector Full control needed → Self-managed on GKE
