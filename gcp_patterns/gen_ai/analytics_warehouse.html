Analytics Data Warehouse — BigQuery

Google Cloud Platform

BigQuery is GCP's fully managed, serverless data warehouse. It separates compute from storage, scales automatically, and supports SQL analytics, ML, and streaming ingestion. Three key architecture views: batch ingestion, streaming ingestion, and client connectivity.

Standard batch ingestion loads data from source systems via scheduled pipelines. Data lands in Cloud Storage or is pulled directly via connectors, transformed by Dataflow or Dataform, and loaded into BigQuery datasets.

Fig 1 — Standard Batch Ingestion Pipeline

Load Patterns

  • Full reload — truncate + reload; simple, safe for small tables
  • Append-only — partitioned tables; time-based partition load
  • Merge (CDC) — Datastream + MERGE SQL for incremental sync

File Formats

  • Parquet / ORC — preferred; columnar, compressed, fast load
  • Avro — schema-embedded; good for streaming exports
  • CSV / JSON — flexible but slower; use for one-off loads

Key Practices

  • Partition tables by ingestion date or business date
  • Cluster on high-cardinality filter columns
  • Use Dataform for version-controlled SQL transforms

Streaming pipelines deliver low-latency data into BigQuery using Pub/Sub and Dataflow. The Storage Write API (with exactly-once semantics) is the recommended ingestion endpoint. Data is queryable within seconds of arrival.

Fig 2 — Streaming Data Ingestion Pipeline

Write API Modes

  • Committed — visible immediately; exactly-once
  • Buffered — batched flush; lower cost
  • Pending — atomic batch commit; ETL use case

Latency Targets

  • Near real-time (<30s) — Pub/Sub → Dataflow → Storage Write
  • Micro-batch — windowed Dataflow with 1–5 min tumbling windows
  • Sub-second — direct Storage Write API from app

Key Practices

  • Partition streaming tables by _PARTITIONTIME
  • Use materialized views for real-time aggregates
  • Monitor Pub/Sub subscription backlog as pipeline health signal

BigQuery exposes multiple access interfaces. Client-side BI tools connect via JDBC/ODBC or native connectors. GCP-native applications use the client libraries or REST API directly. All access is authenticated via IAM.

Fig 3 — Client Application Connectivity

On-premises BI Access

  • Use Simba JDBC/ODBC driver for Tableau, Power BI, Qlik
  • Service account key or Workload Identity Federation for auth
  • VPC-SC + Private Google Access restricts egress to GCP only

GCP-Native Access

  • Looker Studio and Cloud Looker use native BQ integration — no driver needed
  • BigQuery Storage Read API (Arrow format) for high-throughput ML/export
  • BI Engine provides in-memory cache for sub-second dashboard queries

Security Controls

  • Dataset / table / row / column-level IAM
  • Authorized views for cross-project sharing without data copy
  • VPC Service Controls to prevent data exfiltration

Architecture Considerations

Google Cloud Platform

Security

BigQuery operates on a shared-responsibility model. Enforce data access at every layer — project, dataset, table, row, and column. Prevent lateral movement with VPC Service Controls.

VPC Service Controls — define a perimeter around BQ; prevent exfil to unauthorised networks or projects Column-level security — policy tags via Data Catalog; mask PII fields per user group Row-level security — row access policies filter data based on caller identity IAM least privilege — grant roles at dataset level, not project; prefer predefined roles over primitives Authorized views — share query results across projects without granting underlying table access CMEK — customer-managed encryption keys via Cloud KMS for regulated data Audit logs — Cloud Logging DATA_READ / DATA_WRITE logs for all query and table access Workload Identity Federation — federate on-premises service accounts; eliminate long-lived key files

Performance

BigQuery performance is driven by storage layout, slot allocation, and query patterns. Poorly partitioned tables and full-table scans are the most common causes of slow, expensive queries.

Partitioning — partition by ingestion time or date column; prune scanned data by orders of magnitude Clustering — cluster on 1–4 high-cardinality filter/join columns after partitioning Materialized views — pre-aggregate frequently queried results; auto-refreshed; transparent to queries BI Engine — in-memory acceleration for Looker Studio / Looker; eliminates cold-start query latency Slot reservations — use capacity commitments (flex / monthly / annual) for predictable workloads Query optimisation — use column projection, predicate pushdown, and avoid SELECT *; use EXPLAIN to inspect query plans Storage Read API — Arrow-format bulk reads for ML training; bypasses query engine overhead Workload Management — assign slot reservations to projects/folders; isolate prod from dev queries

Monitoring & Observability

Observability in BigQuery spans query performance, slot utilisation, pipeline health, and data quality. INFORMATION_SCHEMA is the primary source of truth for query-level telemetry.

INFORMATION_SCHEMA.JOBS — query history, bytes billed, slot ms, errors; join with user for attribution INFORMATION_SCHEMA.TABLE_STORAGE — table size, row count, last modified; track growth over time Cloud Monitoring dashboards — slot utilisation, query latency p50/p95, reservation consumption Cloud Logging — audit logs for all data access; export to BQ for long-term analysis Dataplex data quality — define rules (null checks, range checks, referential integrity); schedule scans Streaming pipeline monitoring — Pub/Sub subscription backlog, Dataflow system lag, bytes written/s Alerts — Cloud Monitoring alerts on slot quota usage (>80%), query errors, and ingestion lag thresholds

Cost / FinOps

BigQuery costs have two axes: storage (active vs. long-term) and compute (on-demand bytes scanned vs. reserved slots). Most overspend comes from unoptimised queries and missing partitions.

On-demand vs. capacity — on-demand suits spiky workloads; switch to slot reservations above ~$1K/month spend Partition pruning — required filter on partition column eliminates scan cost; enforce via required partition filter flag Long-term storage discount — tables not modified for 90 days charged at ~50% lower rate automatically Cost attribution — label jobs with project/team/pipeline; query INFORMATION_SCHEMA.JOBS for per-team billing BigQuery budgets — Cloud Billing budget alerts per project; set spend alerts at 50% / 80% / 100% Query cost estimation — use dry-run (--dry_run flag) before execution; validate bytes scanned in preview Data lifecycle — expire partitions with partition expiry; delete unused datasets; avoid duplicating tables Flat-rate Editions (Standard / Enterprise / Enterprise+) — predictable cost with autoscaling slots per edition tier
